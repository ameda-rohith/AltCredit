# AltCredit backend

FastAPI service for the rule-based "New-Age" credit score: score + explanation, what-if simulator,
counterfactual target planner, product matching with a bank API hand-off, PDF transparency report,
and an anonymised lender portal. SQLite is embedded, so it is plug-and-play.

## Run

```bash
cd backend
python -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env                                # optional
.venv/bin/uvicorn app.main:app --port 8000          # API -> http://localhost:8000/docs
.venv/bin/uvicorn bank_mock.main:app --port 8001    # partner bank (separate app, API-key protected)
.venv/bin/python -m pytest -q                       # tests
```

First start creates `altcredit.db` and seeds the 500 users from `data/merged_data.json` and 3 lenders.
Demo logins (password `DEMO_PASSWORD`, default `altcredit-demo`): users `USR_001`..`USR_500`,
lenders `primebank`, `microfin`, `neolend`.

## Layout

```
backend/
  data/merged_data.json   user features (seed source)
  core/                   settings, SQLAlchemy engine, password hashing
  services/
    rule_engine.py        the AltCredit rule engine
    score_config.py       tiers, points and thresholds (the engine's single source of rules)
    explainability.py     factor analysis / natural-language explanations
    product_engine.py     product matching against the catalog
    user_service.py       scoring glue (engine + PD + explanation + products) and persistence
    data_parser.py        loaders, missing-data normalisation, transactions -> features
    whatif_service.py     custom what-if edits re-scored by the engine
    target_service.py     counterfactual "what must change to qualify for product X"
    report_service.py     PDF transparency report + JSON export
    seed.py / bank_client.py
  app/                    FastAPI app, models, schemas, routes
  bank_mock/              the separate "bank" application (X-API-Key)
  docs/er_diagram.md      ER diagram (Mermaid), generated by scripts/generate_er_diagram.py
```

Still read from `machine_learning/data/`: the product catalog, transactions, and the ground-truth CSVs used by the tests.
The `machine_learning/engines` scripts have been removed; their reusable parts now live in `services/`.

## Auth

`POST /auth/login`, `/auth/register` and `/auth/register-lender` return `{role, subject, token, token_type,
expires_in}`. Send the token as `Authorization: Bearer <token>`; every route except `/health`, `/products`
(catalog) and `/auth/*` requires it. A token is bound to one account: a borrower token only opens
`/…/{their user_id}/…`, a lender token only `/lender/{their lender_id}/…` (401 without or with a bad/expired
token, 403 for someone else's id).

Tokens are stdlib HMAC-SHA256 signed (`core/security.py`), valid `TOKEN_TTL_MINUTES` (default 480). **Set
`SECRET_KEY` in `.env` for anything shared** (the API logs a warning while the dev default is in use).
Failed logins are throttled per (username, client ip): `LOGIN_MAX_FAILURES` per `LOGIN_WINDOW_SECONDS` → 429.
`GET /scoring/{id}/explain` (paid LLM) is limited to `EXPLAIN_MAX_PER_HOUR` fresh generations per user and caches
results while the score inputs are unchanged. The limiters are in-memory, i.e. per process.

**Lender visibility is consent-based.** Seeded demo users are in the lender pool; new registrants are opt-in
(`share_with_lenders` at signup) and can change it with `PUT /users/{id}/consent`. Opting out hides the
candidate and withdraws open offers (`WITHDRAWN`).

## API (prefix `/api/v1`)

| Area | Endpoints |
|---|---|
| Auth | `POST /auth/login`, `POST /auth/register` (account + demographics + the whole profile; stored in `users` and the first `loan_applications` row) |
| Scoring | `GET /scoring/{user_id}` · `PUT .../profile` · `POST .../transactions` (CSV) · `GET .../history` |
| What-if | `POST /scoring/{user_id}/what-if` with `changes` (absolute values) and/or `deltas` (relative) |
| Target | `GET /scoring/{user_id}/target?product_id=P_04` |
| Export | `GET .../report.pdf` · `GET .../export.json` |
| Dashboard | `GET /dashboard/{user_id}` |
| Products | `GET /products` · `GET /products/{user_id}/recommendations` · `POST .../apply` · `GET .../offers` · `POST .../offers/{id}/respond` |
| Lender | `GET /lender/{lender_id}` · `.../candidates` (filters) · `.../candidates/{anon_id}` · `POST .../offers` · `GET .../offers` |

Lenders only see anonymised leads (`ANON-xxxxxx`); a user's name/email is returned to a lender only after that
user ACCEPTS its offer.

## Assumptions

- **PD is derived, not trained**: `PD = 1 - score/1000`. The data has no default label, so the ML PD model,
  propensity model and PDF OCR are not implemented.
- **Missing data**: `normalise_profile` fills conservative defaults (0 points) and returns `missing_fields`.
  No recorded credit lines/delinquencies scores as "clean" (thin files legitimately have none).
- **Score cap**: raw maxima sum to ~1320 and the score is capped at 1000, so strong users can see smaller what-if
  gains (`score_capped`).
- Seeded users keep their precomputed features; only uploaded statements derive features from transactions.
- ER diagram deviations: string ids (`USR_001`), nullable `is_default`, a profile snapshot on applications,
  `offer_type` on offers, and a `bank_applications` table. Names/emails are synthetic.
